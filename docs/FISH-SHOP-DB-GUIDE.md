# 이음 수산 매입소 — 변경점과 팀 DB 적용 안내

작성: 2026-10-08. 현재 작업 폴더의 시장·온라인 경제 기능에 추가한 구현이다. main 4369d96의 하루·의견함·하루 규칙 변경과 통합했으며, 업적·판매 SQL 번호를 10·11로 변경했다.

## 이번에 추가한 기능

- 시장 서쪽 빈 공간에 **이음 수산 매입소**를 추가했다. 생선 진열대와 간판이 있고, 건물·카운터를 통과하지 못하도록 충돌 판정이 있다. 시장 지도에서도 선택할 수 있다.
- 매입소 앞에서 **E** 또는 화면의 **물고기 팔기** 버튼을 누르면 판매창이 열린다.
- 종류·크기·개별 가격을 확인하고 물고기를 선택해 판매한다. 여러 마리를 한 번에 팔 수 있으며, 한 요청의 상한은 100마리다.
- 물고기 회수, 소지금 지급, 판매 영수증, 돈 이동 기록을 서버의 한 트랜잭션에서 처리한다. 받은 돈은 기존 은행 입금과 옷 구매에 바로 사용할 수 있다.
- 현재 매입 대상은 물고기 7종이다. 쓰레기·동전·옷은 이번 판매점에서 매입하지 않는다.
- 온라인 낚시로 획득한 물고기와 그 물고기를 유저 거래로 받은 경우 판매할 수 있다. 기존 브라우저 보관함에서 가져온 `source='legacy'` 물고기는 기록을 신뢰할 수 없어 판매하지 않는다. 아이템 자체는 유지한다.
- 거래 진행 중인 물고기는 팔 수 없다. 가격이 바뀌면 기존 금액의 판매를 중단하고 새 가격을 보여준다. 판매 전에 다시 선택한 총액을 확인할 수 있다.
- 응답이 끊겨도 동일한 요청 ID로 결과를 재확인한다. 새로고침이나 재접속으로 같은 물고기의 돈을 두 번 받지 못한다.
- 판매해도 이미 획득한 업적과 장착한 칭호는 유지한다. 다른 사람의 물고기를 구매·판매하는 것으로 낚시 업적을 새로 받지는 않는다.

## 팀의 메인 DB에 연결하는 방법

**팀 DB 관리자에게 `database/11_fish_sales.sql`과 이 문서를 전달하면 된다.** 앱은 기존 Supabase 로그인 사용자 ID와 기존 돈·인벤토리 테이블을 공유한다. 별도 판매 DB나 새로운 로그인 서버를 만들 필요가 없다.

1. 기존 경제 기능이 같은 팀 Supabase 프로젝트에 있는지 확인한다. 아래 쿼리는 Supabase **SQL Editor**에서 관리자가 실행한다.

   ```sql
   select
     to_regclass('public.sw_wallets') as wallets,
     to_regclass('public.sw_items') as inventory,
     to_regprocedure('public.sw_economy(text,jsonb,uuid)') as economy_rpc,
     to_regprocedure('public.sw_achievements(text,text)') as achievements_rpc;
   ```

2. 기존 경제가 없다면 이 저장소의 `01_socialworld_base.sql` → `02_loop_schema.sql` → `03_world_update.sql` → `04_coco.sql` → `05_chief.sql` → `06_haru.sql` → `07_feedback_chat.sql` → **`08_economy.sql`** → `09_haru_rules.sql` → **`10_achievements.sql`** 순서로 준비한다. 이미 적용한 파일을 판매 기능 때문에 다시 실행할 필요는 없다. 기존 DB에 경제 기능은 있고 업적만 없다면 `10_achievements.sql`을 먼저 적용한다.
3. **`11_fish_sales.sql` 전체 내용을 SQL Editor에 붙여 넣어 실행한다.** 파일 안에 트랜잭션과 API 스키마 새로고침이 포함되어 있다. 실패하면 그 마이그레이션의 변경은 함께 취소된다.
4. 같은 Supabase 프로젝트에 연결된 최신 `social_world/app/` 또는 재생성한 단일 HTML 데모를 사용한다. 브라우저에서 기존 계정으로 로그인하여 온라인에서 잡은 물고기를 판매한다.
5. 판매 후 인벤토리에서 해당 물고기가 없어졌는지, 소지금이 증가했는지, 은행·옷가게에서 그 돈을 사용할 수 있는지 확인한다. 새로고침 후에도 결과가 유지되어야 한다.

SQL 파일 번호는 `06=하루`, `07=의견함`, `08=경제`, `09=하루 규칙`, `10=업적`, `11=물고기 판매`다. 예전에 `06_economy.sql`이라는 이름으로 동일한 경제 스키마를 적용한 DB는 실제 테이블·함수 유무를 확인하면 된다. 번호를 바꿨다고 기존 데이터를 옮기거나 지울 필요는 없다. 이전에 `09_achievements.sql`·`10_fish_sales.sql`을 적용했다면 새 10·11은 같은 스키마이므로 이름 변경 때문에 다시 실행하거나 초기화할 필요는 없다. 최신 main의 06·07·09와 함께 적용할 때 새 번호 순서를 따른다.

**이번 작업에서는 실제 팀 DB에 SQL을 실행하지 않았다.** 프로젝트와 내 컴퓨터 시험 도구를 업데이트했고, DB 검증은 분리된 시험 DB에서 진행했다. 팀 DB 적용은 위 파일을 사용하는 관리자의 배포 작업이다. `social-world-local-db` 시험 도구는 팀 서버에 배포하지 않는다.

## DB/API 구조

```text
판매창 → OnlineEconomy → Supabase sw_fish_shop RPC
                           ├─ 로그인 사용자·소유권·거래 상태 확인
                           ├─ 서버 매입표로 가격 계산
                           └─ 물고기 삭제 + sw_wallets 소지금 증가
                              + sw_fish_sales 영수증 + sw_ledger 입금 기록
                              + sw_economy_requests 중복 처리 방지
```

| 테이블/함수 | 용도 |
| --- | --- |
| `sw_fish_prices` | 종류별 기본 가격·cm당 가격·매입 여부 |
| `sw_fish_sales` | 판매자, 원본 아이템 UUID, 종류·크기, 지급 금액, 거래 UUID, 판매 시각 |
| `sw_trade_offers.item_snapshot` | 판매·분리수거로 원본 아이템이 없어져도 기존 거래의 아이템 정보 보존 |
| `sw_fish_shop('quote', '{}', null)` | 내 물고기, 판매 불가 이유, 서버 가격, 최근 영수증 20개와 현재 경제 상태 |
| `sw_fish_shop('sell', args, request_id)` | 선택한 물고기를 원자적으로 판매하고 결과·현재 경제 상태 반환 |

판매 인자는 다음과 같다. `request_id`는 같은 논리 요청을 재시도할 때 그대로 사용한다.

```js
await supabase.rpc('sw_fish_shop', {
  p_action: 'sell',
  p_args: { instanceIds: ['보유 물고기의 실제 UUID'], expectedTotal: 970 },
  p_request_id: crypto.randomUUID()
});
```

앱에서는 위 호출을 직접 새로 만들기보다 `economy.sellFish(ids, total)`을 사용한다. 기존 경제 클라이언트가 요청 ID 저장·네트워크 복구·잔액 갱신을 담당한다. 클라이언트의 `expectedTotal`은 가격을 정하는 값이 아니라, 사용자가 확인한 금액과 서버 계산 금액이 같은지 확인하는 값이다.

가격표는 로그인 사용자가 읽을 수 있지만 수정할 수 없다. 영수증은 본인만 읽는다. 아이템과 잔액을 직접 바꾸는 사용자 권한은 추가하지 않았다. 판매 RPC는 기존 경제·업적과 같은 사용자 잠금을 사용한다. 기존 `sw_economy` 함수를 덮어쓰지 않는다.

기존 거래의 아이템 FK는 `ON DELETE CASCADE`에서 `ON DELETE SET NULL`로 바뀐다. 판매된 물고기의 완료·취소·만료 거래는 삭제하지 않고 `item_snapshot`에 원래 UUID와 정보를 남긴다. **추후 거래 내역 화면은 종료된 거래의 `item_id`가 null일 수 있음을 고려하고 `item_snapshot`을 표시해야 한다.** 진행 중인 거래의 아이템은 판매·삭제를 막고, 유효 기간이 지난 대기 거래는 삭제 시 만료 상태로 남긴다. 기존 거래 RPC의 기능은 유지한다.

## 현재 시험 가격

공식 운영 가격은 아직 정해지지 않았으므로 조정 가능한 시험값이다. 공식은 **기본 가격 + floor(크기 cm × cm당 가격)**이며 소수점 이하 원 단위는 버린다.

| 물고기 | 기본 가격 | cm당 가격 | 예시 |
| --- | ---: | ---: | --- |
| 피라미 | 30원 | 3원 | 12.5cm → 67원 |
| 메기 | 100원 | 10원 | 60cm → 700원 |
| 각시붕어 | 25원 | 5원 | 5cm → 50원 |
| 미꾸라지 | 40원 | 4원 | 10cm → 80원 |
| 붕어 | 70원 | 7원 | 20cm → 210원 |
| 잉어 | 120원 | 10원 | 85cm → 970원 |
| 닥터피쉬 | 35원 | 5원 | 6cm → 65원 |

관리자가 조정하는 예시:

```sql
update public.sw_fish_prices
set base_price=120, per_cm=10, enabled=true
where item_id='carp';
```

마이그레이션을 재실행해도 기존 영수증·잔액과 관리자가 조정한 가격은 보존한다. 게임 화폐이며 현금 환전 기능은 없다.

## 내 컴퓨터에서 시험하기

1. 바탕화면 `social-world-local-db`에서 서버가 켜져 있다면 `STOP-LOCAL-DB.cmd`를 실행한다.
2. `START-LOCAL-DB.cmd`를 실행한다. 기존 DB가 버전 1 또는 2라면 필요한 SQL을 적용하여 버전 4로 올린다. 새 main의 하루·의견함·하루 규칙을 추가한다. 기존 잔액·예금·인벤토리·업적은 유지한다.
3. 시험 도구에서 계정 A 또는 B를 고른 뒤 **85cm 판매용 물고기 추가**를 누르면 선택한 계정에 시험 잉어가 추가된다.
4. 같은 계정의 게임을 열고 버스로 시장에 가거나 시장 지도에서 매입소를 선택한다. 매입소 앞에서 E → 잉어 선택 → 1마리 팔기를 누른다.
5. 소지금이 **970원 증가**하고 물고기가 사라지는지 확인한다. 서버를 종료·재시작해도 결과와 영수증이 남아야 한다. 시험 도구의 돈 이동 기록에는 **물고기 매입소 판매**가 표시된다.

이 시험 물고기 추가 버튼은 로컬 시험 도구에만 있다. 팀 DB/일반 앱에는 아이템을 임의로 생성하는 버튼을 추가하지 않았다. 로컬 시험 도구는 외부 Supabase 주소·SDK를 사용하지 않는다.

## 검증

- 분리된 PostgreSQL 엔진에서 판매 46개: 소유권, 크기·출처, 거래 잠금, 일괄 판매, 위조 가격, 금액 변경, 요청 중복, 지급 실패 전체 롤백, 영수증·RLS, 재적용, 소지금 상한.
- 판매 클라이언트 10개: 새 RPC 경로, 마이그레이션 미적용 때 기존 은행 유지, 응답 유실·재접속 후 중복 지급 방지.
- 실제 Chrome 화면 66개: PC·390px 모바일·단일 HTML 데모에서 판매 선택, 총액, 가격 변경, 재시도, 인벤토리·잔액 지속, 은행·옷 구매.
- 판매 SQL 적용 후 기존 경제 56개: 낚시, 분리수거, 은행, 옷, 유저 거래, RLS 및 회계 기록.
- 로컬 DB 버전 2→3 업그레이드·재시작 13개: 잔액·칭호 유지, 판매 HTTP 연결, 영수증 지속, 로컬 격리.

위 191개 확인을 통과했다. 이는 격리된 시험 환경의 결과이며, 실제 팀 Supabase에 적용한 후에는 팀 계정으로 판매 흐름을 확인해야 한다.
