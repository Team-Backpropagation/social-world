# 돈 시스템·온라인 인벤토리 변경 정리

작성일: 2026-10-07 · 대상: 현재 3D 데모의 `social_world/app` 원본과 기존 팀 Supabase

## 현재 상태

은행 입출금, 옷 구매·착용, 온라인 인벤토리, 서버에서 결정하는 낚시 보상을 구현했다. 향후 유저 거래 화면을 붙일 수 있도록 판매 제안·수락·취소·거절을 처리하는 서버 기능과 클라이언트 연결 함수도 추가했다.

**실제 팀 Supabase에는 이 작업으로 SQL을 실행하거나 데이터를 변경하지 않았다.** 코드와 DB 변경 파일을 준비하고, 독립된 PostgreSQL 엔진 및 브라우저에서 검증한 상태다. 아래 DB 적용 절차가 완료되면 온라인 기능이 활성화된다.

## 사용자에게 달라지는 점

| 기능 | 동작 |
|---|---|
| 시험용 돈 | 온라인 지갑을 처음 만드는 계정에 게임 내 화폐 10,000원을 한 번 지급 |
| 은행 | 소지금·예금 잔액 확인, 금액을 입력해 입금·출금 |
| 옷가게 | 셔츠 4종 1,000원, 니트 2종 1,200원에 구매. 같은 종류의 옷은 중복 구매 불가 |
| 옷 착용 | 옷가게 또는 인벤토리에서 입기·착용 해제. 현재 캐릭터의 상의 색에 반영 |
| 인벤토리 | 계정별 온라인 저장. 물고기별 크기·낚은 장소·획득 시각 유지. 옷 분류 추가 |
| 낚시·분리수거 | 온라인 상태에서는 서버가 입질 시간과 보상 종류·크기를 결정하고, 분리수거도 서버에 기록 |
| 연결 확인 | 보관함을 열거나 은행·옷가게를 이용할 때 새로 조회. 접속 중 30초마다 조회하고 창을 다시 활성화할 때도 갱신 |
| 통신 실패 | 마지막으로 받은 아이템·잔액은 표시. 서버가 확인하지 못한 돈·아이템 변경을 브라우저에서 임의로 확정하지 않음 |

기본 낚싯대는 계정에 기본 제공되는 도구다. 낚시로 얻는 ‘작은 동전’은 기존처럼 수집품이며 지갑의 돈으로 자동 환산하지 않는다. 옷 착용 데이터는 온라인 인벤토리 쪽에 저장하고, 기존 프로필의 기본 옷 색은 유지한다. 착용을 해제하면 기본 옷 색이 보인다.

## 기존 브라우저 인벤토리 보존

DB 적용 전에는 기존 브라우저 인벤토리와 낚시를 계속 사용한다. 이때 은행 입출금과 옷 구매 버튼은 사용할 수 없다.

DB 적용 후 계정의 온라인 보관함이 처음 열리면, 그 브라우저의 기존 아이템을 **계정당 한 번** 가져온다. 기존 저장 파일은 지우거나 덮어쓰지 않는다. 물고기 크기·장소·획득 시각과 낚싯대 장착 상태를 가져오고, 기존 분리수거 완료 개수도 보존한다.

- 가져오기 한도는 기존 아이템 2,000개 및 분리수거 기록 2,000개다. 한도를 넘으면 이전을 중단하고 원래 기록을 보존한다.
- 기존 진행 상황이 있는 브라우저에서 먼저 접속해야 한다. 다른 브라우저에서 이미 첫 이전을 끝낸 계정은 나중에 가져온 브라우저 기록을 자동으로 다시 합치지 않는다.
- 기존 브라우저 아이템은 서버가 획득을 검증했던 기록이 아니므로 `legacy`로 구분하고 **현재 유저 거래 대상에서 제외**한다. 온라인 낚시 보상과 구매한 옷은 거래 기반에 연결된다.
- 온라인 보관함을 한 번 불러온 후 통신이 끊기면, 브라우저 저장 모드로 되돌아가 새 아이템을 지급하지 않는다. 연결 복구 후 다시 확인해야 한다.
- 낚시 안내 완료·안내 숨김·지도·효과음·키 설정은 계속 브라우저 설정에 남는다.

## DB에 추가되는 구조

기존 01~05 SQL 및 그 테이블은 변경하지 않았다. 새 파일 `database/06_economy.sql`은 Supabase의 `auth.users`와 `auth.uid()`를 사용한다.

| 테이블 | 역할 |
|---|---|
| `sw_economy_settings` | 새 지갑에 지급할 시험용 지원금 설정 |
| `sw_item_catalog` | 아이템 정의, 옷 가격, 물고기 크기 범위, 분리수거 분류 |
| `sw_wallets` | 계정별 소지금·예금·장착 상태·기존 기록 이전 여부·상태 버전 |
| `sw_items` | 고유 ID별 아이템 소유자·속성·획득 경로 |
| `sw_recycling` | 온라인 분리수거 기록 |
| `sw_ledger` | 돈 지급·이동·차감 기록 |
| `sw_economy_requests` | 처리한 요청 ID와 결과 — 재전송 중복 방지 |
| `sw_fishing_casts` | 서버가 정한 낚시 입질·마감 시간과 사용 여부 |
| `sw_trade_offers` | 판매자·구매자·아이템·가격·거래 상태·만료 시간 |

브라우저는 `sw_economy` DB 함수를 호출한다. 내부 조회 함수 `sw_economy_snapshot`은 일반 사용자가 직접 호출할 수 없다. 사용자에게는 자기 지갑·보유 아이템·기록과 본인이 관련된 거래만 읽는 권한을 주고, 잔액·소유권을 표에 직접 쓰는 권한은 주지 않는다.

은행 입출금은 소지금과 예금의 합을 유지한다. 옷 구매는 돈 차감과 아이템 지급이 같은 DB 작업에서 함께 성공하거나 취소된다. 요청 ID를 저장해 응답이 끊기거나 재접속하더라도 같은 구매·입출금·낚시·거래가 반복 처리되지 않게 했다. 새로고침 응답이 늦게 도착해도 이미 받은 최신 상태를 과거 상태로 덮어쓰지 않는다.

## 유저 거래 기반의 범위

**이번에는 유저 목록·거래 신청창·실시간 거래 알림 화면을 추가하지 않았다.** 현재 사용자 화면은 은행, 옷가게, 인벤토리다. 거래의 서버 처리 및 연결 함수까지 준비한 상태다.

직접 판매 방식의 거래 흐름은 판매자가 아이템·구매자·가격을 지정한 제안을 생성하고, 지정된 구매자가 수락하는 방식이다. 판매자의 제안 생성과 구매자의 수락을 각각 동의로 취급한다. 제안은 10분 후 만료된다.

- 같은 아이템의 진행 중인 제안은 한 개만 생성할 수 있다.
- 착용 중인 옷은 벗어야 판매할 수 있다. 제안 중인 아이템은 장착하거나 분리수거할 수 없다.
- 구매자의 소지금, 판매자의 소유권, 거래 상태 및 만료 시간을 다시 확인한 뒤 돈과 아이템을 함께 이동한다.
- 판매자는 취소하고 구매자는 거절할 수 있다. 제삼자는 거래에 참여할 수 없다.
- 두 계정의 처리는 계정 ID 순서로 잠금을 잡고 진행하도록 작성했다.
- 연결 함수는 `offer(instanceId, buyerId, price)`, `acceptOffer(offerId)`, `cancelOffer(offerId)`, `declineOffer(offerId)`다. 상대방 선택 화면 및 닉네임 검색은 다음 구현 범위다.

## 팀 DB 적용 방법

1. 현재 앱이 사용하는 **기존 팀 Supabase 프로젝트**에 관리 권한이 있는 계정으로 접속한다.
2. SQL Editor에서 `database/06_economy.sql`의 전체 내용을 실행한다. `begin`부터 `commit`까지 한 번에 실행해야 한다.
3. 실행 성공 후 데모를 새로고침하고, 기존 진행 상황이 있는 계정·브라우저로 접속한다.
4. 인벤토리에서 ‘온라인 보관함’ 표시와 기존 아이템을 확인한다. 은행에서 100원 입금·출금 후 소지금+예금 합이 유지되는지 확인한다.
5. 옷가게에서 한 벌을 구매하고, 재접속 후 잔액·보유 여부·착용 상태가 유지되는지 확인한다.

06은 기존 NPC·이벤트 테이블에 의존하지 않는다. 이번 경제 기능을 위해 적용 여부가 불분명한 03~05를 함께 실행할 필요는 없다. 06은 같은 파일을 재실행해도 기존 잔액·아이템·관리자가 바꾼 지원금과 가격을 초기화하지 않도록 작성했다.

브라우저용 Supabase 연결을 그대로 활용하므로 앱에 관리자 키나 DB 비밀번호를 추가할 필요가 없다. 실제 팀 DB 적용 상태는 파일의 기록만으로 확정할 수 없으며, 관리자 화면에서 별도로 확인해야 한다.

시험용 지원금을 끄려면 관리자의 SQL Editor에서 다음을 실행한다. 이미 지급된 잔액에는 영향을 주지 않는다.

```sql
update public.sw_economy_settings set welcome_amount = 0 where id = true;
```

옷 가격을 변경하는 예시는 다음과 같다. 실제 결제는 DB 가격을 사용한다.

```sql
update public.sw_item_catalog set price = 1500 where id = 'sage-shirt';
```

## 로그인과 운영 범위

데이터는 **로그인 계정 ID**를 기준으로 저장한다. 동일 계정으로 로그인하면 다른 기기에서도 동일한 보관함을 사용할 수 있다. 하지만 현재 ‘게스트로 들어가기’는 브라우저의 익명 로그인 계정이므로, 다른 기기에서 새로 게스트로 들어가면 다른 계정이 된다. 실제 기기 간 이용에는 정식 로그인 또는 익명 계정을 정식 계정으로 연결하는 흐름이 필요하다.

지원금 10,000원은 은행·옷가게 시험용 설정이다. 정식 운영에서는 신규 계정 생성 정책과 함께 지급 여부를 정해야 한다. 현재 낚시는 서버가 시간·보상을 확인하지만 캐릭터 위치와 이동까지 서버에서 검증하는 멀티플레이 시스템은 아니다.

현재 조회는 계정의 보유 목록 전체를 가져온다. 대규모 운영에 앞서 목록의 페이지 구분, 서버 요청 제한, 거래 내역 보관 기간, 요청 ID 기록 정리, 실제 여러 DB 접속에서의 동시 거래 부하 검증을 추가할 수 있다. 이미지·3D 모델은 공통 파일을 사용하며 사용자별 아이템 행에 복제하지 않는다.

시장 채팅은 기존처럼 화면 안의 로컬 미리보기다. 이번 돈·인벤토리 온라인 연결이 다른 유저의 채팅이나 캐릭터 이동을 온라인으로 연결하지는 않는다.

## 검증 결과

총 **854개 검사 통과**. DB 56개, 비동기 클라이언트 21개, 온라인 화면 60개, 기존 낚시 135개, 시장·버스 164개, 채팅창 108개, 시계·시장 채팅 154개, 기존 UI 80개, 코코 34개, 이장 42개를 확인했다. 새 온라인 화면 검사는 PC 원본·모바일 원본·PC 실행용 HTML을 대상으로 했다. 기존 화면 검사는 해당 테스트의 PC·모바일·실행용 HTML 조건을 유지했다. 상세 원문은 `social_world/app/tests/ECONOMY-VALIDATION.txt`에 있다. 테스트는 팀 Supabase에 연결하지 않고 PGlite 0.5.8의 실제 PostgreSQL 엔진과 별도의 로그인·화면 테스트 데이터를 사용한다. Supabase 운영 환경에서의 SQL 실행과 실제 계정 두 개를 이용한 최종 확인은 DB 적용 후 진행해야 한다.

## 팀원 재검증 방법

Node.js에 `playwright`, `@electric-sql/pglite@0.5.8`을 준비한다. 브라우저 테스트에는 Chromium 또는 Chrome이 필요하다. 필요하면 `SW_CHROME_PATH`로 Chrome 경로를 지정한다. 외부 CDN이 제한된 환경에서는 `SW_THREE_PATH`로 Three.js 0.149.0 파일 경로를 지정한다.

```text
python social_world/app/bundle.py
node database/tests/economy_test.cjs
node social_world/app/tests/economy_client_test.cjs
node social_world/app/tests/economy_browser_test.cjs
node social_world/app/tests/fishing_test.cjs
node social_world/app/tests/market_test.cjs
```

테스트용 `database/tests/01_auth_stub.sql`은 독립된 테스트 DB에서만 사용한다. 팀 Supabase의 기존 Auth를 대신하도록 실행하면 안 된다.
