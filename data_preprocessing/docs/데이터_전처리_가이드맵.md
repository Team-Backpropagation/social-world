## 1. 데이터 정제 (Data Cleaning)

### 1-1. 로딩 시 인코딩/구분자 — 가장 먼저 틀리기 쉬운 부분

- 카드 데이터(txt): **CP949 인코딩, 탭(`\t`) 구분자**. UTF-8로 열면 `MCT_SGG_CD` 등 한글 컬럼이 깨진다. `pd.read_csv(path, sep='\t', encoding='cp949')`
- 통신 데이터(csv): UTF-8 **BOM 포함**, 파이프(`|`) 구분자. `encoding='utf-8-sig'`로 열어야 첫 컬럼명(`STD_YM`)에 BOM 문자가 안 붙는다.

### 1-2. 카드 데이터(데이터2) 정제 체크리스트

- [ ] **법인 제외 확인**: 스키마 자체에 법인 값이 없음을 재확인(SEX_CCD/AGE_CCD에 `법인`이 남아있으면 로딩 오류이므로 assert로 검증)
- [ ] **CLN_SGG_CD 결측 처리**: NULL이 아니라 **`"정보없음"`이라는 문자열 값**으로 들어있음(전체의 약 1.1%, 20,244행). 정제 시 `"정보없음" → NaN`으로 변환하고, 결측 비율을 로그에 남길 것. 이 컬럼을 "거주자 vs 외지인" 구분에 쓸 계획이므로 결측 처리 방식이 지표에 직접 영향을 준다.
- [ ] **타입 캐스팅**: TA_YMD(문자열 8자리 → datetime), TS_AT/USE_CNT(문자열 → 정수)
- [ ] **PK 중복 체크**: (TA_YMD, MCT_SGG_CD, MCT_RY_CD, CLN_SGG_CD, SEX_CCD, AGE_CCD) 조합이 유일해야 정상 집계 테이블 — 중복 행 발견 시 합산(sum)할지 데이터 이슈로 볼지 팀 논의
- [ ] **업종(MCT_RY_CD) 그룹핑**: 90종 원본 카테고리를 그대로 쓸지, 고립 관련 상위 카테고리(예: 의료/식음료/생필품/여가·유흥/기타)로 재분류할지 결정 — 재분류 매핑 테이블을 이 단계에서 확정해두면 이후 지표 설계가 쉬워짐
- [ ] **이상치 점검**: TS_AT 최대값이 중앙값 대비 매우 큰 롱테일(관측됨) — 결제 오류가 아니라 정상적인 고액 업종(가구·가전 등) 집계일 가능성이 높으므로 무작정 제거하지 말고 업종별 분포로 먼저 확인

### 1-3. 통신(유동인구) 데이터 정제 체크리스트

- [ ] **⚠️ 최우선 적용 — 12월 파일 중복행 제거 (실측 확인 완료, 2026-09-18)**: `flow_time_pop_202512.csv`, `flow_wkdy_pop_202512.csv` 두 파일은 **전체 행이 정확히 2배로 완전 중복**되어 있음(값까지 100% 동일한 완전 중복, 부분 중복 아님).

## 2. 분할기준 (Data Split Criteria)

### 2-1. 이 프로젝트에서 "분할"이 일반적인 ML 문제와 다른 이유

- 개인 단위 라벨이 없다 — 지도학습의 표준적인 train/test 랜덤 분할 개념을 그대로 쓸 수 없음
- 기간이 6개월(184일)뿐 — 계절성 파악 불가, holdout을 너무 길게 잡으면 baseline(평상시 프로파일) 추정 자체가 불안정해짐
- 통신(월별 6포인트)과 카드(일별 184포인트)의 시간 해상도가 달라 **같은 분할 기준을 두 데이터에 그대로 적용할 수 없음**

### 2-2. 권장 분할 축 — 3가지를 병행 적용

**① 시간 분할(Temporal Split) — 가장 중요, primary 기준**

- 목적: "코호트별 평상시 활동 프로필(baseline)"을 앞부분 데이터로 추정하고, 이후 기간의 이탈 여부를 이상탐지 관점에서 평가하는 구조에 맞춘다.
- **확정(2026-09-21): 2분할이 아니라 3분할로 변경.** baseline 113일 / event 18일 / eval 53일
  - **baseline**(7/1~10/31 중 이벤트 제외, 113일) — 평상시 프로파일 산정
  - **event**(4구간 18일: 7/16~17, 8/15, 10/3~9, 12/24~31) — 버리는 게 아니라 **이벤트 반응도 측정 대상**
  - **eval**(11/1~12/23 중 이벤트 제외, 53일) — 추세 이탈 검증
  - 변경 이유: 기존 2분할은 baseline에 추석이, eval에 연말이 섞여 양쪽 모두 오염된 상태였다.
    추석 당일 강남 결제는 평소의 44% 수준까지 떨어진다(데이터_분석근거_정리.md 2·12절)
  - 이벤트 구간 선정은 공휴일 달력 + 자동 탐지 병용. `src/config.py`의 `EVENT_PERIODS` 참고
- 대안: 고정 split 대신 **walk-forward(직전 N일 이동평균 대비 최근값 이탈도)** 방식도 검토할 만함 — 대회 요구사항인 "실시간 지수화"와 방향이 더 맞을 수 있음
- **금지 사항**: 날짜를 무작위로 train/test에 섞는 random split은 절대 쓰지 말 것 — 시계열 데이터에서 미래 정보가 baseline에 leak되어 이상탐지 성능이 실제보다 부풀려짐

**② 공간 분할(Spatial Split) — 지역은 분리 유지, 홀드아웃 대상 아님**

- 강남구·춘천시는 인구구조가 다른 지역(강남=청년형 추정, 춘천=고령·청년 이중구조 가설)이므로 하나의 pooled 모델로 합치지 말고, 지역을 covariate로 포함하거나 지역별로 baseline을 따로 산정
- 두 지역 모두 최종 산출 대상(그 지역 자체의 위험도를 내야 함)이므로, 일반화 검증을 위해 한 지역을 통째로 holdout하는 방식은 이 프로젝트 목적에 맞지 않음 — 대신 **각 지역 내부에서** 위 ①의 시간 분할을 각각 적용

**③ 코호트 분할 — 분석 단위 자체를 쪼개지 않는다**

- 분할은 반드시 "코호트×시점" 레벨에서 이루어져야 함. 데이터가 이미 집계되어 있어(개별 트랜잭션이 없음) 코호트를 무작위로 train/test에 나누는 것은 의미가 없다
- Cross-validation이 필요하면 코호트는 고정하고 시점만 나누는 시계열 CV(예: `TimeSeriesSplit`) 방식을 쓸 것

### 2-3. 지도학습을 시도할 경우의 라벨/검증 분할 (선택 트랙)

- KOSIS 고독사 통계는 지역×연도 단위 통계라 코호트×일별 라벨이 아니다 — 이걸로 엄밀한 train/test 분할을 만드는 건 불가능. **"사후 상관관계 검증"으로만 사용**하고 진짜 test set이 아니라는 점을 보고서에 한계로 명시할 것(로드맵 리스크 항목과 동일한 결론)
- 만약 자체 규칙 기반 "약한 라벨"(예: 특정 분위수 이하를 위험으로 가정)을 만들어 지도학습을 시도한다면, 그 경우에도 train/test 분할은 여전히 ①의 시간 기준을 따를 것 — 라벨이 규칙 기반이라 해서 랜덤 분할이 정당화되지는 않음

### 2-4. 최종 권장안 요약

1. **1차 기준 = 시간**: 지역별로 baseline 기간 / 평가 기간을 분리(예: 7~10월 vs 11~12월)
2. **지역은 분리 유지**: 강남구·춘천시를 pooling하지 않고 각각 안에서 시간 분할
3. **코호트는 분석 단위로 고정**: 코호트를 쪼개는 분할은 하지 않음
4. **외부 라벨(고독사 통계 등)은 test set이 아니라 참고 검증 지표**로만 위치시키고, 이 한계를 보고서에 명시

## 3. Phase 2 체크포인트와의 연결

로드맵상 9/30 체크포인트가 요구하는 "코호트 단위로 정리된 통합 데이터셋 v0"은 곧 이 문서의 1절(정제) 산출물이며, 2절(분할기준)은 그 데이터셋을 Phase 3(EDA)·Phase 4(모델링)에서 어떻게 나눠 쓸지의 규칙이다. 정제 코드와 분할 코드는 분리된 스크립트/노트북 셀로 유지해, 나중에 baseline 기간을 바꾸는 실험을 할 때 정제부터 다시 돌릴 필요가 없게 할 것.
