# 사회적 고립 AI 에이전트 — 데이터 전처리

통신(SKT 유동인구)·카드(신한카드) 원본 데이터를 정제해 **코호트 단위 분석용 데이터셋(v0)** 을 만드는 코드입니다.
로드맵 Phase 2(9/24~9/30) 산출물이며, `데이터_전처리_단계별_실행가이드.md`의 Step 1~13을 모듈로 옮긴 것입니다.

원본 데이터는 이 저장소에 포함되지 않습니다. **각자 대회 사이트에서 받아 `DATA/` 폴더에 넣어야 합니다**(아래 2단계).

---

## 1단계. 설치 (처음 한 번만)

필요한 패키지는 pandas, numpy 두 개뿐입니다.

```bash
pip install -r requirements.txt
```

**파이썬 버전**: 3.12.10 기준입니다. 코드 자체는 3.8 이상에서 동작하지만,
3.12에서는 `pandas 2.1+`, `numpy 1.26+`가 필요합니다(그 이전 버전은 3.12용 빌드가
없어 설치가 실패합니다). `requirements.txt`의 하한이 이 기준으로 잡혀 있습니다.

버전 확인:

```bash
python --version
python -c "import pandas, numpy; print(pandas.__version__, numpy.__version__)"
```

## 2단계. DATA 폴더 준비

코드를 받은 폴더 안에 `DATA` 폴더를 만들고, 대회에서 받은 원본 파일 **19개**를 넣습니다.

```
받은 폴더/
├─ DATA/                  ← 직접 만들고 원본 19개를 넣으세요
├─ run_pipeline.py
├─ requirements.txt
└─ src/
```

넣어야 하는 파일 19개입니다.

| 구분 | 파일 | 개수 |
|---|---|---:|
| 통신 성연령 | `flow_age_pop_202507.csv` ~ `202512.csv` | 6 |
| 통신 시간대 | `flow_time_pop_202507.csv` ~ `202512.csv` | 6 |
| 통신 요일 | `flow_wkdy_pop_202507.csv` ~ `202512.csv` | 6 |
| 카드 결제 | `신한카드_빅콘테스트2026_데이터2.txt` | 1 |

`신한카드_..._데이터1.txt`(주제1 기후 트랙용)와 테이블 정의서 xlsx는 **실행에 필요하지 않습니다.**
넣어도 무해하지만 코드가 읽지 않습니다.

준비가 됐는지 확인하는 명령이 있습니다.

```bash
python run_pipeline.py --check
```

누락된 파일이 있으면 파일명을 하나씩 알려줍니다. `DATA`를 다른 위치에 두고 싶으면
`python run_pipeline.py --data-dir D:/경로/DATA` 처럼 지정할 수 있습니다.

## 3단계. 실행

```bash
python run_pipeline.py
```

약 100초 뒤(파일 캐시가 데워져 있으면 30초대) **41개 검증 항목이 모두 `OK`** 로 나오고
`clean/` 폴더에 산출물 10개가 생깁니다.
하나라도 `다름`이 나오면 그 자리에서 멈추고 팀에 공유해주세요(원본이 교체되었거나 코드가 수정된 것입니다).

처음에는 카드 데이터만 먼저 돌려 환경을 빠르게 확인하는 것을 권합니다(약 16초).

```bash
python run_pipeline.py --only card
```

### 업종 테이블을 따로 둔 이유

메인 코호트표(`card_cohort_daily.csv`)는 업종을 합쳐버립니다. 그래서 설계 노트에서 지표
후보로 올려둔 **"소비처가 편의점 위주로 좁아지는지(업종 다양성)"**, **"병의원·약국 결제 비중
급감"** 같은 업종 기반 지표를 만들 수 없습니다. 그 지표를 쓰려면 `card_industry_*.csv` 가
필요합니다.

설계 판단 두 가지를 기록해둡니다.

- **연령대는 원본 9구간(10~90대)을 유지**했습니다. 고령 고립 분석에서 70/80/90대를
  '60대이상'으로 묶으면 약국·병의원 패턴의 차이가 사라지기 때문입니다. 통신과 비교할 때 쓸
  6구간(`age_group`)은 파생 컬럼으로 함께 들어 있습니다.
- **거주여부(resident)는 넣지 않았습니다.** 업종과 교차하면 행이 약 65만으로 늘고 셀이
  과도하게 희소해집니다. 거주자/외지인 분석은 메인 코호트표로 충분합니다.

업종 다양성 지표를 계산할 때 **일별보다 월별(`card_industry_monthly.csv`)을 권합니다.**
일별은 건수 10 미만인 희소한 셀이 약 9%라 다양성 지표가 크게 흔들립니다.

### 업종 지표를 만들기 전에 팀이 정해야 할 것

1. **`ZZ_나머지`** 는 원본의 기타/미분류 버킷입니다. 업종 다양성을 셀 때 이것을 하나의
   업종으로 볼지 제외할지 정해야 결과가 안정적입니다.
2. **`세금공과금`, `학교등록금`, `통신요금(이동,시내전화)`, `보험`** 등은 생활 고정지출로
   "사회적 활동 반경"과 성격이 다릅니다. 고립 지표에서 분리하거나 제외할지 검토가 필요합니다.
3. **90종을 상위 카테고리로 묶을지** — 확정되면 `src/config.py` 의 `INDUSTRY_GROUP_MAP` 에
   `{"약국": "의료", "일반병원": "의료", ...}` 형태로 채우기만 하면 됩니다.
   그러면 업종 테이블에 `industry_group` 컬럼이 자동으로 생깁니다(매핑에 없는 업종은 '미분류').

산출물은 약 300MB이고 원본에서 언제든 재생성할 수 있으므로 **저장소에 커밋하지 않습니다**
(`.gitignore`에 `clean/`, `DATA/` 제외 설정이 들어 있습니다).

## 코드를 수정할 때 알아둘 것

### 절대 건드리지 말 것
- `DATA/` 폴더 — 읽기 전용입니다. 원본이 훼손되면 대회 사이트에서 다시 받아야 합니다.
- 통신 로딩의 `drop_duplicates()` — 12월 시간대·요일 파일에 완전중복 행이 있습니다.
  제거하지 않으면 12월 수치가 2배로 부풀려져 11월→12월 비교가 전부 "급증"으로 오판됩니다.
- `cohort.build_flow_cohort()`의 "집계 먼저 → melt 나중" 순서 — 순서를 바꾸면
  행이 715만 개로 불어나 메모리가 터집니다(RAM 4GB 환경에서 실측 확인).
- `split.add_split_label()` — 3분할(baseline / event / eval) 구조이며, 무작위 분할
  (`train_test_split`)로 바꾸지 마세요.
  시계열 데이터에서 미래 정보가 새어들어가 성능이 실제보다 좋게 나옵니다.
  심사에서 가장 지적받기 쉬운 지점입니다.

### 바꿔도 되는 것 (팀 논의로 확정될 항목)
`src/config.py`의 다음 값들입니다. 바꾼 뒤에는 해당 단계만 다시 실행하면 됩니다.

- `BASELINE_END` — baseline/eval 경계일 (현재 `2025-10-31` 잠정치)
- `EVENT_PERIODS` — baseline에서 제외할 이벤트 구간(명절·연말 등). 현재 4구간 18일.
  event 구간은 버리는 게 아니라 이벤트 반응도 측정 대상이다
- `REGION_EVENT_CANDIDATES` — 지역별 특이 구간. 팀 확정 전이라 아직 적용하지 않음(기록용)
- `REGION_MAP` — 경계 격자 셀을 포함하기로 방침이 바뀌면 필터 로직 조정
- `AGE_CODE_MAP` — 연령대 라벨 표기

### 성능 관련 주의
- `apply(axis=1)`을 쓰지 마세요. 180만 행을 한 줄씩 처리해 수 분이 걸립니다.
  `np.where`나 `map`으로 컬럼 단위 연산을 하면 순식간입니다(`clean_card.add_resident` 참고).
- 통신 3종을 동시에 메모리에 올리지 마세요. `run_pipeline.py`는 한 테이블씩
  처리하고 `del`로 반환하는 구조입니다.

## 검증 기대값은 어디서 왔나

`src/config.py`의 `EXPECTED`에 있는 숫자는 2026-09-18에 실제 원본 데이터로 파이프라인을
돌려 측정한 값입니다. 코드가 이 숫자를 재현하지 못하면 둘 중 하나입니다.

1. 원본 파일이 교체·수정되었다 → 대회 측 재배포 여부 확인
2. 코드가 수정되어 결과가 달라졌다 → 변경 의도가 맞는지 확인 후 `EXPECTED` 갱신

임의로 `EXPECTED`를 실제값에 맞춰 고치면 검증의 의미가 없어집니다.
갱신이 필요하면 왜 달라졌는지 팀에 공유한 뒤 함께 바꿔주세요.
